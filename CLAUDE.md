# warp-lite: agent notes

- `main` is production. Each task gets its own branch from `main` and enters through a PR after Diego's OK. Never push to `main` directly.
- **Release**: a push to `main` runs `.github/workflows/release.yml`. It builds with `tools/build.sh --local`, then publishes `vX.Y.Z` in this repo. The tag points at the pushed commit (`--target`). Assets: `warp-lite-setup.exe`, `warp-lite.exe`, `warp-lite.zip` (the bare exe) and a `.sha256` next to each (sha256sum format). Installed copies update themselves from `releases/latest` (they look for the asset named `warp-lite-setup.exe`, so that name never changes).
- **No release when nothing that ships changed** since the previous tag. Shipped paths: `src third_party assets tools/build.sh .github/workflows/release.yml warp-remote` (warp-remote.exe, the phone sidecar, goes inside the installer). The run still ends green.
- **Is it in production?** Look at `releases/latest`, never at the green check. A merge is in production when that release's tag contains it, or when the merge changes none of the shipped paths. dcbot closes a task as «✅ En prod» only when its health check passes: `prod-check release justdiegocom/warp-lite <clone> warp-lite-setup.exe warp-lite.exe warp-lite.zip warp-lite-setup.exe.sha256 warp-lite.exe.sha256 warp-lite.zip.sha256 -- src third_party assets tools/build.sh .github/workflows/release.yml warp-remote`. It also checks every `.sha256` asset against the digest GitHub computed for the file it names. If the shipped paths or the assets change in `release.yml`, change that check in dcbot's `projects.toml` too. By hand: `gh release view -R justdiegocom/warp-lite`, then `git merge-base --is-ancestor <merge> vX.Y.Z`.
- **One process per Warp**: every window of an instance (`%APPDATA%\warp-lite`, or a test's `WARPLITE_DIR`/`WARPLITE_SESSION`) lives in the process that started first; a later start hands its request to it (hidden window `WarpLiteHost`) and exits. Window state is in `struct Window` (`g_win` is the one being handled; reader threads never touch it, they post to `g_host`). Tests (`tools/wintest-*.ps1`, run by hand) name windows with the `label:` step, not by pid; `wintest-recuperar` crashes Warp on purpose and checks every window comes back.
